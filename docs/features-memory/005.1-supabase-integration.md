# Memoria Técnica: 005.1 - Integración con Supabase

## Propósito
Este documento registra el hito de integración técnica donde conectamos el backend de NestJS con la base de datos real en Supabase, migrando el esquema de datos y eliminando las simulaciones en memoria del motor de lealtad.

## Componentes Implementados

### 1. Cliente Tipado (Supabase MCP)
- Se utilizó la herramienta MCP de Supabase para autogenerar los tipos de TypeScript (`database.types.ts`) directamente desde el esquema de la base de datos de producción.
- Se implementó un `SupabaseService` global que inicializa un cliente con **Service Role Key** para permitir al backend ejecutar operaciones administrativas esquivando el Row Level Security (RLS) en rutas donde se procesa lógica del servidor.

### 2. Autenticación de Cajeros (Módulo 003)
- Se creó el método `loginEmployee(businessId, pin)` dentro de `EmployeesService`.
- **Seguridad**: El sistema busca a los cajeros activos del negocio y utiliza `bcrypt.compare` para validar el PIN proporcionado contra el `pin_hash` almacenado de forma encriptada en la base de datos, evitando guardar o transmitir pines en texto plano.

### 3. Motor de Lealtad (Módulo 005)
- Se refactorizó por completo el servicio `LoyaltyEngineService.processScan`.
- **Flujo de Base de Datos**:
  1. Recibe el UUID del pase escaneado.
  2. Valida la existencia de la instalación en la tabla `pass_installations` usando `.single()`.
  3. Extrae la información anidada (relacionada) del pase, el negocio y el programa de lealtad (para conocer la meta de sellos `stamp_goal`).
  4. Realiza un `.select()` de la tabla `stamp_transactions` filtrando los sellos válidos y calcula el acumulado actual.
  5. Inserta la nueva transacción (`stamp_count = 1`) para el cajero y el cliente correspondientes.
  6. Envía el parche (PATCH) a Google Wallet con los datos reales provenientes de Supabase y fuerza la Notificación Push.
- **Modo Híbrido (Red de Seguridad)**: Se introdujo una comprobación de expresión regular (`isUUID`) en el payload del QR. Si el escáner detecta un ID de prueba (como `alan-test-123`), el motor entra en modo "simulación", inyectando números aleatorios para evitar romper las demos en vivo, demostrando un excelente manejo de la retrocompatibilidad durante el desarrollo.

## Estado de la Base de Datos
- El esquema oficial quedó documentado en `docs/database-schema.md` e inyectado a través del panel SQL en Supabase.
- El flujo de validación y estampado es ahora **100% transaccional** y atado a IDs reales.
